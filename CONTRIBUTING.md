# Contributing to Sumcheck

## Getting a working tree

```bash
npm run build
```

That fetches the vendored dependencies (pinned versions, recorded in
`vendor/VERSIONS.json`), verifies the committed icons and regenerates
`THIRD_PARTY_NOTICES.md`. `vendor/` is not in the repository — 6 MB of
third-party binaries do not belong in the history — so **a fresh clone will not
convert anything until you run it**. There are no `npm install` dependencies:
everything the extension uses at runtime ships inside the package.

## The two gates

Both must be green before anything lands:

```bash
npm test                                   # conversion cases, headless Chrome
npm run verify-extension -- <a.pdf>        # the MV3 wiring, real install
```

`npm test` covers the conversion engine through a dev server serving the
extension's real CSP. `verify-extension` covers what only a browser has — the
service worker, context menus, `chrome.storage.session`, the password dialog,
queue rendering, localisation — and installs the packaged zip to check the
artifact that actually ships. Give it a PDF and it converts one end to end.

Before publishing: `npm run check` and `npm run package`.

## Fixture-first

**Add a failing fixture before the fix, and keep it after.** Not a
suggestion — this codebase has twice had a change that passed every synthetic
test and broke every real document. If a bug is worth fixing it is worth a
fixture that reproduces it, and the fixture should look like the real input, not
like a convenient one.

Conversion cases go in `test/harness.js`. UI behaviour that only exists in an
installed extension goes in `scripts/verify-extension.mjs`. Fixture files are
generated by `scripts/make-fixtures.mjs` rather than committed as opaque blobs,
so they can be regenerated and inspected.

## Never silently rewrite a value

The one rule the whole project is organised around. If a converter is unsure
about a figure it says so, in the output, where a reader will see it. It does
not correct it. On a price list a converter that quietly "fixes" a number is
worse than one that is visibly wrong.

New validators belong in `src/core/validate.js` and follow the same shape:
suggest, mark, never mutate.

## Measure, don't assert

Claims about accuracy are backed by a score against a ground-truth corpus, not
by reasoning. `npm run audit -- <dir>` converts a directory of real documents;
`npm run score-export <out-dir> <groundtruth.json>` scores the result and
**exits non-zero if the review-marker invariant breaks**. If you change anything
in the conversion path, run both and put the numbers in your PR.

Screenshots and icons are the exception that proves it: a passing build tells
you nothing about whether a picture is right. Look at it.

## The DEVLOG

`docs/DEVLOG.md` is the project's honest record, newest first. It says what was
found, not just what was changed — including measurements that turned out
wrong, and the corrections that followed. Corrections are **appended, never
edited in place**: an entry that was wrong stays, with the correction after it,
because rewriting it would falsify the history that makes the rest credible.

If you land something substantial, add an entry in the same shape.

## Style

Match the surrounding code. Comments explain *why*, especially when the code
looks odd — most of the odd-looking code here is odd because the obvious version
broke on a real document, and the comment says which one.
